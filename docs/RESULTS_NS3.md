# NS-3 Evaluation Campaign & Sim-to-Sim Transfer Results (Phase N)

All numbers below are **measured** (ns-3.48, 1000 runs: 5 scenarios x 10 policies x 20 eval seeds) and come from
`results/ns3_campaign/summary/` (see `results/ns3_campaign/README.md` for method and limitations) and
`results/sim_vs_ns3/`. The best-case view is generated by `ns3-sim/analysis/find_best_cases.py`.
This file replaces an earlier draft whose numbers pre-dated the campaign and were not supported by it.

## 1. What was evaluated

```
[ Python simulator (sim/) ] -- trains --> [ DQN seeds 0-4, frozen ]
                                              |  export: dqn_seedN.txt (plain weights)
                                              v
[ ns-3 gateway app ]  C++ forward pass (ns3-sim/dqn-policy.h), 1 AP + 4 STA, 802.11n HT20 2.4 GHz
        |  per 100 ms slot: observe AoI/RSSI -> pick node -> GRANT -> DATA reply -> CSV + UDP telemetry
        v
[ tools/demo_server.py ] -> [ dashboard/static/index.html ]
```

- The DQN is **not** run through gym or Python inside ns-3. Gym is used only for training; the policy runs as
  a C++ forward pass checked against the NumPy version (`tests/test_ns3_policy_parity.py`).
- The network is a packet-level 802.11n simulation (CSMA/CA, real MAC/PHY), not hardware.
- Decision D-N3: the policy stays frozen (no retraining); the sim-to-ns3 gap is reported as measured.

## 2. Scenarios (S0-S4)

| Scenario | Setting |
|---|---|
| S0 Nominal | 5/8/12/18 m, 20 dBm TX |
| S1 Weak links | TX -5 dBm: far links near the loss cliff (STA-4 about -79 dBm) |
| S2 Co-channel interferer | interferer 30-150 s, plus 20% extra loss on STA-4 while it is on |
| S3 Mobility | STA-4 walks 18 m to 45 m and back at 1 m/s, TX 5 dBm |
| S4 Fault | urgent STA-2 down 60-90 s |

Metric: criticality-weighted AoI (weights 10/10/3/1), mean over slots, then over runs; lower is better.

## 4. Where the DQN does best (`results/ns3_campaign/summary/best_cases.md`)

1. **Large, consistent wins over non-AoI-aware policies** (table above): 8-13% over Round Robin, about 50% over Random,
   about 80% over Fixed Priority in S0-S3.
2. **Tail safety under stress.** Mean worst-case urgent-node AoI (s):

   | scenario | DQN | Max-Weight | CAG | Round Robin |
   |---|---|---|---|---|
   | S1 | 2.03 | 2.17 | 2.08 | 1.79 |
   | S2 | 1.97 | 1.92 | 1.92 | 1.55 |
   | S3 | 1.86 | 2.11 | 2.12 | 1.58 |

   DQN has a lower worst-case urgent AoI than Max-Weight and CAG in S1 and S3 (about 12% in S3), but Round
   Robin is lowest in all three. This is a modest, honest advantage, not a headline.
3. **Single best runs (selected, not averages).** Of 500 single-seed DQN runs, 139 beat the better of Max-Weight/CAG
   and 25 do so by more than 3%. The best five are S3 and S1 runs (DQN seed 1 or 3) at -5.7% to -7.3%
   (e.g. `S3_dqn1_seed118`: 0.148 vs Max-Weight 0.159). The dashboard replays these with the caveat that they are the
   best of 500. Pooled over all runs, DQN is +5.4% worse than the better heuristic.

## 5. Sim-to-ns3 gap (D11.1) (`results/sim_vs_ns3/sim_vs_ns3.md`)

- Rank agreement between the Python simulator and ns-3 (Kendall tau): S1 1.00, S2 0.87, S3 0.87, S0 0.73, S4 0.47.
  Rankings are mostly preserved in S0-S3; S4 reorders.
- Python and ns-3 differ in channel parameters (about 25% vs 6% wasted slots in nominal) and run length, so compare
  rankings and relative differences, not absolute AoI.
- In Python the DQN is -2.5% vs CAG and +0.4% vs Max-Weight (a tie); in ns-3 it is +3-5% worse. The transfer gap is about
  5 percentage points against the strongest heuristics.

## 6. Threats to validity

1. S2's interference is modelled as extra loss on STA-4 plus real co-channel traffic, which alone caused no measurable loss.
2. S4's fault window is 60-90 s (the protocol says 30-60 s); its urgent-violation metric includes the dead node.
3. The 802.11 PHY has an abrupt association cliff (about -15 dBm TX); scenarios stay above it.
4. The "DQN (no shield)" ablation is not implemented in the ns-3 build.
5. All results are simulation; none are from hardware. Single BSS, one AP.
6. The dashboard's recorded replays use one eval seed (100) and 120 s runs; the campaign uses 20 seeds and 300 s.

## 7. Prepared panel answers

**Q: Is the DQN really running inside ns-3? Through gym?**
The frozen policy's weights are loaded from a text file and a C++ forward pass picks the node every slot. There is no
Python or gym at run time; gym was only used for training in the Python simulator. A parity test checks the C++ output
against the NumPy implementation.

**Q: Why use ns-3 if training happens in a Python simulator?**
Training needs about 500,000 steps, which is impractical inside ns-3. We train fast in Python and evaluate the frozen
policy zero-shot in a high-fidelity 802.11 stack to test transfer.

**Q: Does the DQN beat the baselines?**
It clearly beats Round Robin (8-13%), Random (about 50%) and Fixed Priority (about 80%). Against Max-Weight and CAG it is
about 5% worse on average (training seeds 1-3 average 0.5-3% worse, seeds 0 and 4 about 10% worse); it ties CAG in
weak-link conditions. Its distinct advantages are lower worst-case urgent AoI in S1/S3 than those two, and that it learns
the policy rather than being hand-coded. We report the full distribution and flag the best-case runs as selected.

**Q: Why doesn't it beat Max-Weight?**
Max-Weight is near-optimal for this small 4-node problem with a fairly clean channel; there is little headroom, so a
learned policy can at best match it. The Python-simulator result (a tie with Max-Weight) agrees. In S4 the DQN does worse: the other
nodes' peak AoI during the fault is much higher than for the heuristics.

**Q: Why do the seeds differ so much?**
Training seeds 0 and 4 converged to a worse policy (about 10% worse). We report all five, and the demo seed (1) was
selected after seeing the ns-3 results; this is disclosed in the dashboard and here.

**Q: What if a sensor node dies?**
In S4 liveness masking stops grants to the unreachable node (a recovery probe is re-sent every 2 s). The DQN recovers in
about 0.67 s on average (up to 2 s in the worst run), similar to Max-Weight/CAG (0.63 s) and slower than Round Robin
(0.16 s); the dead node's own AoI still grows for the whole outage.
